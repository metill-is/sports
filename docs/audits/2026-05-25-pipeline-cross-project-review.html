The sports pipeline, end to end

Data flow across metill-is/sports and metill-is/metill-platform, with a path to ad-hoc model re-runs.

TL;DR. The pipeline produces 133 JSON files across 13 cells (9 football + 2 basketball + 2 handball), all rsync'd hourly into metill-platform and served behind FastAPI on Fly.io. The architecture is healthy: facts → beliefs → decisions → publish with explicit freshness predicates, and the per-fit extracts tree at data/beliefs/extracts/ decouples publishing from re-fitting.

The headline gap is the one you asked about — model replay infrastructure exists but has no clean entry point. fit_league(end_date=...) works, 03b_backfill_football_iceland.R uses it with hardcoded dates, and republish.yml can render JSONs from any past extract. What's missing is a single CLI: scripts/0Nr_replay.R --league X --sex Y --as-of YYYY-MM-DD. That, plus three honesty fixes (meta.json::fit_date, drift schema between repos, the GITHUB_TOKEN deploy chain), would close ~80% of the friction.

4 · Findings

Ordered by impact on your stated goal (re-run + re-export). Severity tags follow the convention in the rest of your project rules.

F1 · headline

Model-replay infrastructure exists but has no entry point

fit_league(end_date = D, schedule_horizon_days = 200L) already produces a fit "as of date D" using only data available then. extract_football_iceland() writes the per-division extracts. publish_one() reads from any fit_date partition. republish.yml can re-render JSONs in seconds. All the pieces are there.

What's missing is a single CLI: Rscript scripts/0Nr_replay.R --league football_iceland --sex male --as-of 2026-05-15 [--publish-to data/publish_replay/]. Section 5 has a concrete proposal.

Today: replay only happens via the hardcoded date list in scripts/03b_backfill_football_iceland.R. The function chain works; the surface doesn't.

F2 · honesty

meta.json::fit_date lies about model freshness

The field is set from format(end_date, "%Y-%m-%d") at publish time, not read from the resolved extracts partition. The 2026-05-12 incident: women's BD shipped fit_date="2026-05-11" while the underlying posteriors were from 2026-05-04 (9 days stale). The bug is acknowledged in Sports/Knowledge/Publish Pipeline/data-contract.md but the fix hasn't shipped.

This becomes a blocker for any replay workflow — if you re-publish with a fit from May 5 but fit_date shows today, the consumer can't tell.

Likely culprit: R/publish-football-iceland.R · the meta.json assembler. Pin fit_date to the value embedded in extracted$fit_date (which read_extracted_football() already returns from the partition path).

F3 · sync

pull-sports-data.yml commits don't trigger deploy.yml

GitHub policy: pushes made with the default GITHUB_TOKEN don't fire other workflows' on: push triggers. So when the hourly pull commits new JSONs, deploy.yml doesn't run and production lags until the next human push to metill-platform main. Documented in the vault's next-actions.md; no fix yet.

Two clean fixes, pick one:

  • (a) Add workflow_dispatch: to deploy.yml and call gh workflow run deploy.yml at the end of pull-sports-data.yml (still uses GITHUB_TOKEN, but explicit dispatch does fire workflows).
  • (b) Use a PAT with workflow scope as secrets.SPORTS_DATA_PUSH_TOKEN when pushing. Trades convenience for a token to rotate.

metill-platform/.github/workflows/pull-sports-data.yml · final git push step.

F4 · drift

No schema validation between the two repos

The contract is "filenames + JSON shapes." When a sports-side refactor renames a field (e.g. p_top_six → p_european) or adds a new required key, the platform's chart silently goes blank. The vault calls this out as a critical risk but nothing enforces it.

Lightweight option: write JSON Schemas alongside config/leagues.yml (you already have schemas/leagues.schema.json, this would be the publish-side companion), validate in scripts/05_publish.R before writing, and validate again in metill-platform's pull-sports-data.yml after rsync. Either side failing closed prevents broken pages.

New files: config/publish-schemas/{meta,standings,team_strengths,...}.schema.json. Validator: jsonvalidate::json_validate() on R side, fastjsonschema on Python side.

F5 · maintainability

Backfill dates are hardcoded in 03b

scripts/03b_backfill_football_iceland.R hardcodes the pre-round-N fit dates (5 entries for 2026 season). Adding a new league or starting a new season means editing the script. Better: derive the missing pre-round dates from the schedule + the gaps in data/beliefs/extracts/.../fit_date=*/ partitions.

Pseudocode: for each (league, sex, round) where the round's first kickoff is in the past, ensure an extract partition exists with fit_date < first_kickoff. If not, queue a fit.

If you ship the replay CLI from F1, this becomes "generate the list and pipe to xargs" rather than a separate script.

F6 · coverage

Basketball + handball can't be replayed at all

They still load the fit RDS directly in publish_basketball_iceland() / publish_handball_iceland(). The RDS is ephemeral (gitignored, ~500 MB), so "what did we publish on date X" is unrecoverable without re-fitting from scratch — and the random-seed Stan run won't match.

Plan-wise this is the autumn 2026 work the vault notes. Worth scheduling before the next basketball season starts so the first fit lands in the extracts tree from day one. Schema-alignment with football (the 9-cell team_strengths grid, goal_diff_distribution) is a separate question to settle.

R/publish-basketball-iceland.R, R/publish-handball-iceland.R, R/extract-football-iceland.R as the template.

F7 · category

round_predictions_history.json doesn't belong in data/publish/

The file is read by the publisher itself (it powers team_expected aggregation for standings.json's cumulative xG), not by metill-platform. It still ships to data/publish/, gets rsync'd, sits in data/ithrottir/, and is never read. Wastes ~20 KB × 9 cells per cell on every sync; more importantly, it's a category error that confuses future readers.

Move it to data/beliefs/extracts/.../round_predictions.parquet and read from there in the publisher.

Documented in vault as "pending re-homing." Cheap win.

F8 · UX

No archive of past published JSONs

data/publish/ is overwritten in place every fit cycle. Once you publish today's JSONs, yesterday's predictions are unrecoverable except by re-fitting with end_date = yesterday. That's cheap if extracts are still archived — but a tiny data/publish_archive/YYYY-MM-DD/ mirror written by 05_publish.R would let metill-platform show "predictions over time" without any backend work.

Equivalent: a single Parquet table data/publish_archive/predictions_long.parquet with one row per (fit_date, cell, file, key, value) — easier to query, smaller on disk, gives you the time-series for free.

Either implementation enables a "spá frá X. apríl" toggle on each chart. Cheap; high user value if you ever want to talk about model evolution.

F9 · docs

Replay contract isn't documented

The Obsidian vault is genuinely strong on the publish-pipeline data contract, but has no section on "how to deterministically re-run the model for a historical date." Once F1 ships, write a short note in Sports/Knowledge/Publish Pipeline/ covering: the CLI, the determinism guarantee (Stan seed handling), what data is available pre-round-N for football, and the archive retention policy.

5 · Headline recommendation — replay CLI

This addresses the explicit ask: "re-run any models for this season and re-export the data for predictions or cumulative xP calculations." Concrete, small-scope proposal.

Surface

# Re-fit + re-publish for a single date (in-place; overwrites data/publish/)
Rscript scripts/0Nr_replay.R --league football_iceland --sex male --as-of 2026-05-15

# Re-fit + re-publish into an isolated tree (safe for what-if analysis)
Rscript scripts/0Nr_replay.R --league football_iceland --sex male --as-of 2026-05-15 \
  --publish-to data/publish_replay/2026-05-15/

# Backfill a whole season's worth of pre-round fits (replaces 03b)
Rscript scripts/0Nr_replay.R --league football_iceland --sex male --season 2026 --per-round

# Just re-publish from existing extracts (no fit) — already exists as republish.yml,
# expose it locally too
Rscript scripts/0Nr_replay.R --league football_iceland --sex male --as-of 2026-05-15 --no-fit

Implementation sketch

New file: scripts/0Nr_replay.R

Single entry point. Parses args via parse_pipeline_args() (extend it; today it accepts --league + --sex + --force). Adds --as-of, --season, --per-round, --no-fit, --publish-to.

Reuse existing functions, no new fit logic

The script is a thin orchestrator:

if (!args$no_fit) {
  fit_league(
    league_key = args$league, sex = args$sex,
    end_date = args$as_of,
    schedule_horizon_days = 200L,
    write_archive = TRUE     # to data/beliefs/archive/.../fit_date=as_of/
  )
  # extract_football_iceland() is called internally
}

publish_one(
  static = load_static(args$league),
  betting = NULL,           # decisions are skipped in replay mode
  key = args$league,
  sex = args$sex,
  root = args$publish_to %||% "data/publish",
  fit_date = args$as_of     # NEW: pass through so meta.json honours it
)

Fix F2 inline

Change publish_one() + publish_football_iceland() to accept an explicit fit_date argument and use it for meta.json::fit_date instead of Sys.Date(). Default to extracted$fit_date (which already comes from the partition path). This is a 5-line change and fixes the honesty bug for both replay and normal publish.

Determinism

Stan's HMC uses RNG seeds; without pinning, two runs of fit_league(end_date = "2026-05-15") produce statistically equivalent but numerically different posteriors. For exact replay, pin the seed:

fit_model(..., seed = as.integer(format(end_date, "%Y%m%d")))

This matches what simulate-cup-bracket.R already does for bracket pairings. Cheap, makes replay reproducible.

--per-round derives dates from the schedule

Read data/facts/schedules/.../season=2026/, compute the kickoff date of each round's first match, output fits with end_date = kickoff - 1 day for each round where the partition doesn't already exist. Fixes F5 (hardcoded backfill dates) for free.

--publish-to enables what-if analysis safely

Writing to data/publish_replay/<date>/ instead of data/publish/ means you can re-fit, inspect, compare to today's predictions, and throw it away — without disturbing the live cron pipeline. Add a .gitignore entry for data/publish_replay/ so these don't accidentally ship.

Cumulative xP / xG: already there

This is worth saying explicitly — standings.json::xpts is already lookahead-free cumulative expected points per round, sourced from round_predictions_history. If you want the time series at the team level (xP trajectory across the season), it's already in standings_history.json. If you want it in a more analytical shape (single Parquet with fit_date · team · round · xg_for · xg_against · xpts), F8's archive table gives you that.

So the question to answer first: what specifically do you want xP for that the current standings don't give you? A different time slicing? A leaderboard with cumulative xP shown alongside actual? Export for an external notebook?

Scope estimate

The replay CLI (F1) + fit_date honesty (F2) together: roughly one focused session. The skeleton already exists in 03b_backfill_football_iceland.R — the work is generalising it, wiring args, and adding the fit_date pass-through. Determinism via seed-pinning is a one-line addition.

F3 (deploy chain) is independent and small — a YAML edit on the metill-platform side. F4 (schema validation) is the largest discrete item and worth doing on its own day. F7 + F9 are documentation cleanups.

F1+F2 are the prerequisites. F5 falls out of F1 for free. F8 is a comfortable next layer once F1 is in.

6 · Other improvements worth tracking

Stale-extract guard on the platform

The platform currently trusts whatever JSON it gets. A two-line check in _build_league_context() — if generated_at is older than 48h, surface a small "Spá ekki ný" badge — closes the perception gap when the upstream pipeline silently fails. Belt-and-braces alongside F3.

Stable extract retention policy

Football extracts are accretive — every fit writes a new fit_date=D/ partition and they never get cleaned. Storage growth is modest (~50–100 MB/year per league) but it's worth documenting that they're permanent so a future tidy-up doesn't accidentally delete them. They're load-bearing for replay.

Lookahead audit for new replays

The lookahead-free cumulative-xG logic relies on "each round's xG comes from the latest fit strictly before that round's first kickoff." A single test that picks a known historical fit and verifies its standings.json::xpts matches a hand-computed value would catch silent regressions when extraction logic changes. Today there's no such guard.

OG cards for cup pages

Small UX miss: cup URLs fall through to the generic "Greining og spár · Íþróttir" OG card because the OG generator only handles BD/LD. Easy fix on the platform side — use tournament_placements.json::summary (top 4 favourites + P(champion)) as the card content for cup cells.

Two basketball/handball things to settle now

Both are seasonally paused, but two questions are cheaper to answer cold than hot:
