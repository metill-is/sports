The two questions, answered

1 · How well is it set up for automated data + model handling — and the path to health checks

SET-UP TODAY: Strong skeleton, thin safety net. The automated handling of data and models is genuinely well-architected — and the live evidence proves the machinery runs unattended: federation results scraped 08:18 today, the fit-decide-publish chain fires on every odds/fit success, freshness predicates (needs_refit / has_upcoming_games, R/pipeline-freshness.R) short-circuit redundant work, write_table does atomic staged-rename writes with per-table Arrow schemas (R/storage.R:65,152), upsert_table already keys results on the division-inclusive natural key, the Stan fit ABORTS on divergences>1% / R-hat>1.05 / bulk-ESS<100 (R/model-fit.R:161), the ledger is guarded at the git layer by a pre-commit hook + auto-commit, and ~58 testthat files assert invariants. That is a B-grade automation substrate. The GAP is automated HEALTH CHECKING, and it is the difference between runs and runs correctly. Three holes, all confirmed in code: (1) VALUE BLINDNESS — every storage check is structural; a home_score of -1000, odds of 0.5/Inf/NaN, or a 2027-dated result are valid int32/float64 and flow straight into the Kelly stake formula and Stan likelihood (validate_against_schema, R/storage.R:65, checks column-presence + type ONLY). (2) NO LONGITUDINAL MEMORY — the Stan gate computes div_frac / max_rhat / min_ess_bulk then DISCARDS them (RDS gitignored), so divergences creeping 3 to 80 under the 1% gate, or R-hat drifting 1.004 to 1.012, are invisible until a red CI run; settled-ledger PnL is never aggregated, so a calibration regime break surfaces only as an unnoticed losing streak; an orphaned bet (team-name drift, voided fixture, never-scraped result) sits settled=FALSE forever with no tripwire. (3) NO ALERTING + SILENT-SUCCESS — grep finds NO notification channel in the repo, and the live runs show the cost: scrape-odds FAILED 2026-05-29 11:24 with zero signal, and the published football JSON that fly.metill.is serves is currently ~1-2 days stale, because several code paths return success while producing stale/empty output (odds scrape returns 0 rows invisibly, publish swallows a missing-extract read error, commit-only-if-changed makes a never-ran cron indistinguishable from a clean no-op). CONCRETE PATH TO AUTOMATED HEALTH CHECKS (the same shape recurs in all six dossiers; deduplicated it is one spine): a single pure read-only R function pipeline_health(root, now) in a new R/health.R that composes the existing reads (freshness predicates + a NEW persisted Stan-diagnostics store + a read-only ledger orphan/pool/reconciliation scan + per-store value-freshness) and returns a tibble of {check, scope, status OK<WARN<FAIL, value, threshold}. It WRITES its verdict to a NEW data/health/ tree (status.json + freshness/diagnostics/orphans Parquet) that is itself the committed, diffable, greppable health-status-as-a-file — never touching data/decisions/ledger/, so it is CI-safe by construction (a reader of committed Parquet cannot race the local placer's non-atomic write). A thin scripts/07_healthcheck.R wraps it; a new healthcheck.yml cron runs it ~30 min after the fit chain settles, fails on hard breach, and fires ONE free ntfy.sh curl on failure (the single permitted channel) — with GitHub's native failure-email as the zero-config backup. Thresholds live once in a config/slo.yml + .claude/rules/health-contract.md SLO table that a lockstep test keeps in sync with pipeline_health(). This is entirely within stack (R + testthat + GitHub Actions + git-as-DB + one curl) and reuses the proven test-placer-ci-isolation grep pattern to MACHINE-CHECK that the health workflow stays read-only on the ledger. Build order: persist diagnostics + value-guards first (Phase 0-1), then the pipeline_health spine (Phase 2), then the cron + SLO contract + runbooks (Phase 3).

Confirm intent · do not auto-fix

Four behaviours that look like bugs but are documented-intentional

Any health check or fail-loud edit must surface these as confirm-intent, not silently "fix" them — or it will generate false alarms and erode trust in the signal.

  • fail-silent-to-loud (b) schedule fail-open

    CONFIRM INTENT before touching R/schedule-active.R:28,45. The default_all_active() fall-open on a missing/unreadable schedules dir is documented as deliberate cold-start safety. The proposal says it only SURFACES a degraded flag rather than removing the behaviour — that is the correct posture, but the edit still touches the fail-open code path. Maintainer must confirm: (1) the fail-open stays, (2) the degraded flag is additive-only, (3) a degraded read for >1 cycle warns but never aborts the run. Do NOT let any health check treat all-active-by-default as a fault.

  • fail-silent-to-loud (a) odds 0-row abort

    CONFIRM INTENT: changing R/ingest-lengjan-odds.R:345-347 from silent return(0L) to cli_abort-when-in-season makes scrape-odds.yml go RED on a total scrape failure (good — that is exactly the 05-29 11:24 case). But the abort condition keys on has_upcoming_games()==TRUE, which depends on the schedules data being fresh. If schedules are themselves stale/empty (the fail-open case above), the in-season predicate could misfire and either over- or under-alert. Maintainer must confirm the in-season gate is evaluated against trustworthy schedule data, and that a legitimate all-off-season day still exits 0 cleanly. This is the one fail-loud edit that changes CI exit codes, so it needs an explicit sign-off.

  • healthcheck.yml + reconcile job (read-only ledger access on CI)

    CONFIRM the read-only contract is machine-enforced, not just asserted. healthcheck.yml and any ci-tests reconcile job will READ data/decisions/ledger/ — which is fine (a reader of committed Parquet cannot race the placer's non-atomic write) — but this must be GUARDED by a new test-healthcheck-ci-isolation.R mirroring test-placer-ci-isolation.R, grepping the workflow for any write/place/settle symbol. The no-CI-ledger-writer rule is the single hardest money-path invariant; a future careless edit that adds a settle_ledger() call to the health workflow would corrupt the canonical money record. The isolation test is non-negotiable and must land in the SAME PR as the workflow, not after.

  • QW1 pre-Kelly input guard (quarantine vs abort severity)

    CONFIRM the chosen severity. The guard adds a dropped_invalid_input stage and quarantines bad bets rather than hard-aborting the nightly decide run. That is the right default (one malformed market should not kill all recs for the night), but it is a money-path-adjacent behaviour change: a quarantined bet is a bet that does NOT get placed. Maintainer should confirm quarantine-and-continue (not hard-abort) is the intended failure mode, and that dropped_invalid_input bets are loudly visible (cli_alert + counted in status.json), so a systematic upstream fault surfaces rather than silently suppressing recommendations night after night.
